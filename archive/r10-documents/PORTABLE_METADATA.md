# Portable capture metadata — proposal v0.1

2026-11-09 / 設計案。アプリとNAS連携は未実装。会話内モックの保存はメモリ内のみ。

## 分ける概念

| 概念 | 役割 | 例 |
|---|---|---|
| 保存先フォルダ | 長期的な大分類・物理保管先 | 家族写真、仕事写真 |
| イベント | 開始日・終了日を持つまとまり | 20261109〜10 レゴランド |
| タグ | 日付・保存先をまたぐ複数の検索軸 | 長女、初めて、ジェットコースター |
| ☆ | 特に残したい記録 | お気に入り |
| コメント | 内容・出来事を自分の言葉で記す | 長女が初めてジェットコースターに乗ったよ |

イベントはフォルダ名だけに埋め込まず、ID、名称、開始日、終了日をメタデータに保存する。NAS上は `家族写真/20261109〜10 レゴランド/` のようなサブフォルダに配置する案。イベントの作成・選択で家族／仕事という保存先を勝手に変えない。タグ検索は複数イベント・フォルダを横断する。

モックは1記録1イベント、タグは複数。複数イベントへの所属は未確定。イベント未指定を許し、記録を先に行える。期間による自動割当は提案候補で、日付が一致するだけで無断分類しない。イベント解除は元写真の削除ではない。

## アプリ内DBだけに閉じ込めない

- アプリDBは索引・キャッシュとして再構築可能にする。原メディアと付随メタデータをNASへ移すだけで情報が残ることを目標とする。
- 一般的な項目はXMP、イベントの期間・編集版の親子関係・添付ファイルは文書化されたUTF-8 JSONにも保存する。
- XMPの対応案：星評価 `xmp:Rating`、タグ `dc:Subject`、コメント `dc:Description`（lang-alt）。XMP Ratingは0〜5と-1を扱う。初期モックは☆を0/1に対応させる操作案。既存の1〜5評価や不明なタグを勝手に潰さず保持すること。単純なお気に入りと5段階評価の最終マッピングは実装前に確定する。
- 対応する写真・動画へのXMP埋込と外部 `.xmp` の扱いは媒体・NASソフトごとに検証する。原本のビット列を保つならまずsidecarへ書く。外部ソフトが全sidecarを自動読込するという保証はしない。
- イベント名は一般タグに併記できるが、正式な期間・IDはJSONが保持する。副本間で競合した場合は明示的に解決し、NAS側の変更を無言で上書きしない。
- メタデータ、音声、編集版をメディアとセットでコピー。ファイル名だけで紐付けず、安定UUIDと原本ハッシュを実装時に使用する。移動・改名・重複取込にも対応する。
- Secretのメタデータや音声も同じ保護対象。暗号化記録をNASへ平文で書き出す設定を通常記録と共用しない。

## JSONの提案形式

以下はサンプル。`demo-*` はモック専用IDで、本番ではUUIDへ置換する。`schema` は自作形式の版識別子であって、既存業界標準の名前ではない。

```json
{
  "schema": "theta.capture/1",
  "asset_id": "demo-3",
  "media": "20261109_1423_003.jpg",
  "folder": "家族写真",
  "event": {
    "id": "lego-trip",
    "name": "レゴランド",
    "start": "2026-11-09",
    "end": "2026-11-10"
  },
  "favorite": true,
  "rating": 1,
  "tags": ["長女", "初めて", "ジェットコースター"],
  "comment": "長女が初めてジェットコースターに乗ったよ",
  "versions": [
    {
      "id": "v1",
      "name": "手書き版",
      "source": "20261109_1423_003.jpg",
      "annotations": {
        "strokes": [{"points": [[0.2, 0.3], [0.3, 0.4]]}],
        "text": "はじめて！",
        "voices": [],
        "cutMode": "keep",
        "a": 0,
        "b": 24,
        "duration": 24,
        "hasCut": false
      }
    }
  ],
  "audio_memos": [
    {"file": "20261109_1423_003_voice_1.m4a", "duration_ms": 6200}
  ]
}
```

- ストローク座標は表示に依存しない0〜1の正規化値。回転・トリミングの変換情報と座標原点を本番スキーマで定義する。
- 動画範囲は秒。音声長はミリ秒。写真には本番では不要な動画フィールドを入れない。
- `annotations.text` は編集版の視覚的なメモ、トップレベル `comment` は記録自体の説明。どちらも検索対象とする。
- 編集レシピを他の写真アプリが直接再現できるとは限らない。原本・編集レシピに加え、通常のJPEG／MP4として表示できる編集結果を別名保存することも必要。
- 読み戻し時は未知の項目を保持し、JSON破損、原本不在、音声欠落を個別に扱う。

## 検証項目

アプリ削除／DB再構築後に、ファイル群だけからイベント・タグ・☆・コメント・原本と別版の関係を復元する。NASへの中断転送、同名ファイル、NAS側の改名・コメント更新、Unicode、日本語日付ラベル、別PCでの読込みを確認する。対応を確認した外部ソフト名と項目を記録する。

## R10: 動画の章・結合・静止画抽出

`chapters` は原動画基準の時刻（time_seconds）・ID・titleを保持。`source_frame` は抽出元asset ID・フレーム番号・時刻・fpsを参照するモック形式。本番はフレームPTS／timebaseも保持し、可変fpsで単純換算しない。編集版の `sequence` は原動画assetIdと開始／終了位置の配列を保持し、順序を結合順とする。モックの範囲は30fpsのフレーム単位、終了は排他的。本番では原素材のtimebaseに基づく型を確定する。原本メタデータと編集出力のチャプターは別管理し、編集に応じて出力時刻を再計算する。
